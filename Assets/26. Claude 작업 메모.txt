26. Claude 작업 메모 — 다른 컴퓨터·새 대화에서 같은 방식으로 이어 가기 위한 메모
작성일: 2026-10-20 (Claude의 메모리를 그대로 옮김. 메모리는 컴퓨터마다 따로라 이 파일로 남김)

>>> Claude에게: 새 대화를 시작하면 이 파일을 먼저 읽고, 아래 방식대로 진행할 것.
    그다음 20번(기획) → 23번(남은 할 일, 맨 위 ">>> 다음 수업") → 24번(끝낸 것) → 25번(질문 노트)의 순서로 필요한 곳을 읽음.
    시작할 때 23번 맨 위의 진도와 "★ 먼저 할 것"을 사용자에게 짚어 줌.

======================================================================
1. 지금 하고 있는 일 — 선생님·학생 수업으로 게임 로직을 처음부터 다시 만들기
======================================================================

- 2026-10-20 사용자: "AI가 지금까지 거의 다 작성했다보니까 내가 내 게임의 구조를 잘 모르더라고",
  "선생님과 학생이 공부하면서 제작하는 느낌으로 가보자". 결과물보다 배우는 과정이 목적.
- 교재 = 23. 리팩토링 계획서 (전체 틀, 스크립트 169개 목록, 48수업 설계). 21번 구현 계획서는 보지 않음 ("21번은 무시해도 돼").
- 한 수업의 흐름: 배울 것("왜 필요한지"부터) → 기획(20번의 장) → 설계 → 사용자가 직접 씀 → Claude가 리뷰 → 확인(테스트·씬).
  확인을 통과하면 그 수업을 24번으로 옮기고 23번에서 지우고, 23번 맨 위 ">>> 다음 수업: N"을 올림.
- 사용자는 전체 틀을 처음에 다 정해 두길 원함 ("미리 전체적인 틀을 잡아놓으라니까"). 수업 중 설계를 바꾸면 23번의 목록·개수도 함께 고침.

2. 가르치는 방식 — 사용자에게 맞춘 것
======================================================================

- 사용자는 읽고 이해하는 것은 잘하지만 빈 화면에서 쓰기는 어려운 단계.
  말로 된 힌트·주석 뼈대만으로는 "하나도 모르겠다"가 됨. 거의 완성된 코드에 빈칸 한두 개(★)를 뚫어 주는 방식이 잘 맞음.
  그래도 막히면 완성 코드에 줄마다 설명을 붙여 보여 주고, 같은 모양의 다음 것은 직접 쓰게 함. "정답 보여 줘", "네가 해"면 씀.
- 코드를 통째로 써 넣지 않음. 한 번에 많이 주면 "너무 어려워", "?? 뭐하라고"가 나옴 → 단계를 잘게 쪼갬 (예: 길만 먼저, 스폰은 나중에 복사).
- 비유가 잘 먹힘 (카페 점장 = 싱글톤, 주소록 = BoardGrid, 택배 상자와 책장 = 매개변수와 필드, 그물과 체 = bounds와 HasTile).
  작은 실제 예시(길 5칸짜리 판)로 보여 주면 덜 어지러워 함.
- 사용자가 코드를 자기 말로 풀어 설명할 때:
  뜻이 분명히 맞으면 "맞음"으로 시작하고 넘어감. 표현을 따져 고치지 않음 (두 번 지적받음: "자리가 있다면이 (비어)있다면이지",
  "내가 이해한게 맞음 니가 깐깐하게 보는거임").
  표현이 두 가지로 읽히면 고치지 말고 "○○라는 뜻으로 이해하신 거 맞아요?"라고 한 줄로 먼저 물음 (사용자가 정한 방법).
  동작을 분명히 잘못 알고 있을 때만 바로, 짧게 짚음.
- 같은 설명을 길게 반복하지 않음. 사용자가 "계속 이야기하고 있잖아"라고 하면 짧게 핵심만. 그래도 "이해가 안 감"이면 넘어가지 말고,
  어디서 막혔는지 짐작 하나를 말하고 확인함 (예: OnGetEnemy의 On = "~할 때"라는 이름 때문에 헷갈림).
- 설명이 섞여 헷갈리게 했으면 표로 한 번에 정리함 (해도 되는 것 / 하면 안 되는 것).
- 졸리거나 지쳐 보여도 사용자가 계속하겠다고 하면 계속함 ("퇴근까지 계속 달리긴 할건데").

3. 문서 넷의 역할
======================================================================

20. 통합 기획서      규칙과 기획. 사용자는 "기획"이라고 부름.
23. 리팩토링 계획서  남은 할 일만 (끝난 것은 지움, [x] 같은 완료 표시를 남기지 않음).
24. 리팩토링 내역서  끝낸 수업의 기록: 만든 파일, 수업 중 정한 것, 배운 것의 요점, 확인 상태(테스트 통과 / 씬에서 확인 / 유니티 검증 필요).
25. 수업 질문 노트   사용자가 수업 중·뒤에 한 질문과 답. 부탁받지 않아도 질문에 답한 그 턴에 해당 수업 구역에 Q/A로 더함.
                     Q는 사용자가 한 말에 가깝게, A는 다시 읽어도 이해되게 요점만. 힌트 요청·"왜 오류 나?"도 적음.
                     코드(문법·구조·오류·테스트)에 관한 질문만 적음. 기획 내용을 확인하는 질문은 적지 않음
                     (사용자가 "2107은 몇 티어?"를 직접 지우며 "중요하지 않은 질문(기획쪽)").
26. 이 파일           Claude가 지킬 방식.
(21·22번은 옛 흐름의 문서. 22번의 옛 버그 기록은 23번 4장 [4-7]로 모아 둠)

규칙
- 20번 기획과 문서·코드가 부딪히면 기획(20번 본문의 확정 규칙)을 따르고 다른 쪽을 고친 뒤 알림. 묻지 않음.
  확정 규칙끼리 부딪히면 그때는 물음.
- 20번에는 지금 유효한 규칙만. 대체된 옛 규칙·닫힌 질문·"정해지기 전의 기록"은 남기지 말고 그 자리에서 고쳐 씀. 질문 전에 본문부터 확인.
- 수업 중에 규칙을 바꾸면 20번을 먼저 고침 (예: 버프·디버프 컬러 화이트·블랙 → 옐로우·퍼플, 칸 크기 1.5 → 1).
- 타워 직업(컨셉) 이름을 정할 때 기존 스킬명에 맞추지 않음. 스킬명은 직업에 맞춰 나중에 고침 (효과는 그대로).

- 새 코드: Assets/3. Scripts/New/ 아래 00. Core ~ 12. Dev. 모두 namespace SquareTD.
  테스트는 Assets/Editor/Tests/New/ (namespace SquareTD.Tests), 에디터 도구는 Assets/Editor/New/, 새 프리팹은 Assets/2. Prefab New/.

  그때까지 확인은 DebugCheat 키, 로그, 씬 뷰 Gizmos, Click Debug 창. 로직은 UI를 모르게(이벤트만).
- 타일 이펙트(특수 타일 위성·기포, 디버프존 위성, 길 화살표 점멸, 존 빛남, 칸 강조, 장판 그림)는 계획에서 뺌. 나중에 새로 만듦.
  옛 파일은 지우지도 고치지도 않음. 에디터 도구(SharedVisual 테마 색상, UITilePanelEditor)는 그대로.
- 옛 코드는 지우지 않고 참고서로 둠 (옛 규칙이 남아 있어 정답지는 아님). 마지막 수업(48)에서 정리.
- 이름이 옛 코드와 겹치는 것 주의: 옛 코드는 namespace가 없어 namespace 밖에서는 옛 것이 먼저 찾아짐 (TowerEmblem, EnemyData 등).
- 수치는 미정(20번 12장). 코드는 규칙대로, 수치는 CSV·ScriptableObject에서.
