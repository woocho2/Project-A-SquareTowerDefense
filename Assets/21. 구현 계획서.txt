0. 읽는 순서
======================================================================

문서 셋의 흐름 (2026-10-14 확정): 기획(20번) → 구현 계획서(이 문서) → 구현 내역서(22번)
- 20번 기획: 게임의 컨셉과 구조를 미리 정의한 것.
- 21번 구현 계획서: 기획에 맞춰 코드를 어떤 구조로, 무엇을 고치고, 어떻게 리팩토링할지 정의한 문서.
- 22번 구현 내역서: 이 문서의 항목 중 코드로 구현한 것을 날짜와 함께 "~를 ~로 바꿨다 / ~방식으로 구현했다"로 적는 문서.
- 구현한 항목은 Unity 검증을 마치지 않았어도 22번에 적고 "유니티 검증 필요"로 표시함.
- 끝난 것은 이 문서에서 바로 지움 (완료 표시를 남기지 않음). 항목 전체든 항목 안의 한 줄이든 같음. 확인만 하고 끝난 것도 지움.
- 테스트에서 버그나 오류가 나오면 그 내용을 이 문서에 다시 적음 (5장의 해당 단계나 맨 앞 "버그" 항목).

1) 규칙은 「20. 통합 기획서.txt」. 이 문서에는 규칙을 다시 적지 않고 "20번 ○장"으로 가리킴.
2) 무엇을 어떤 순서로 할지는 5장. 위에서부터 차례로 하면 됨.
3) 파일을 고치기 직전에는 2장(실행 흐름), 3장(소유권 표), 부록 A(스크립트별 메모)에서 그 파일을 찾아볼 것.

이 문서를 쓰는 법
- 커밋은 퇴근할 때 하루치를 한 번에 함. 항목은 하루 안에 끝낼 수 있는 크기로 잡음. 항목마다 "어디"(파일·함수), "할 일", "확인"(끝났는지 보는 법)을 적었음.
- 표시:  [ ] 아직 / [부분] 일부 되어 있음 (무엇이 되어 있는지 적음).
- 옛 작업 번호(A-1, E-1, F-2, G-22 등)는 20번과 22번이 가리키므로 해당 항목 끝에 (옛 G-22)처럼 적어 둠.
- 규칙을 바꾸는 항목은 Assets/Editor/Tests/GameRuleTests.cs의 기대값도 함께 고칠 것.
- 순서를 이렇게 잡은 까닭: 판의 규칙(순환·한도) → 적 → 타워의 공통 틀 → 문양 → 모드·경제 → 구조 정리.
  문양 14종은 공통 틀 위에 올라가므로 틀이 먼저이고, 구조 정리를 뒤에 둔 것은 규칙이 고정돼야 무엇을 어디로 나눌지가 정해지기 때문.
  다만 문양을 옮기면서 그 문양의 옛 코드는 그때그때 지움 (5장 4단계의 "지울 것").

2. 실제 실행 흐름 (지금 코드)
======================================================================

[2-1] 게임 시작과 한 웨이브

GameManager.OnStartGame()
  → Idle 상태, 기존 turnRoutine 중지
  → TurnLoopRoutine(): 웨이브마다
      → CheckEnemyLimit(): 소환 전 잔존 적 수 > 한도면 게임 오버, 새 적을 만들지 않음
      → EnemyManager.SpawnWaveRoutine(): WaveManager.SpawnWaveEnemies()로 웨이브 구성 전부 소환 → 모든 큐브 착지 대기
      → EnemyWaveRoutine(): PlayerTurnRoutine 1번 → EnemyTurnRoutine 10번
          → 40웨이브면 최종 보스가 살아 있는 동안 적 턴을 계속 반복 (보스의 제한 턴 20이 다 되면 게임 오버로 끝남)
          → 종료 상태가 아니면 WaveManager.NextWave()
          → TowerManager.ProcessEarthTowerWave(완료 웨이브)                         ← 5장 1-9에서 삭제
      → 다음 웨이브의 소환 전 판정

- turnRoutine은 '누구 턴인가'가 아니라 실행 중인 코루틴 핸들.
- EnemyTurnRoutine 끝에 WaitForSeconds(0.3f)가 있음.
- NextWave()는 완료한 웨이브가 40 미만일 때만 호출됨. 웨이브 번호는 40에서 멈춤.

[2-2] 적 1턴 — GameManager.EnemyTurnRoutine()

  ① ProcessEnemyMovement()
      → EnemyManager.ProcessEnemyTurnRoutine()
          → 적마다 EnemyMoveController.ProcessTurnMoveRoutine(), 모든 이동 완료 대기
  ② ProcessTowerSupport()
      → TowerManager.BeginEnemyTurnForTowers(): 이전 타일 버프 기록, 타워 상태 시간 감소
      → ExecuteSupportTowerActionTurnRoutine(): 버프/디버프 타워 실행, 그 뒤 타워가 자기 타일의 스택형 버프 기록을 읽음
  ③ ProcessTileBuffs()
      → EnemyManager.ApplyAllTileBuffs() → 적마다 EnemyMoveController.CheckAndApplyTileBuff()
          → 타일 스탯 초기화 → 멈춘 타일의 속도/방어/회복 적용 → EnemyDebuffController.RefreshTileDebuffs()
  ④ ProcessTowerAttacks()
      → TowerManager.ExecuteAttackTowerActionTurnRoutine()
          → 타워별 스킬 확인(TryUseSkill) → 타워 기본 행동 → 활성 투사체가 없어질 때까지 대기
  ⑤ ProcessDamageDebuffs()
      → EnemyManager.AdvanceAllDebuffTurns() → 적마다 EnemyDebuffController.AdvanceDebuffTurn(): 상태 시간, 도트 피해, 조건부 즉사
  ⑥ EnemyManager.AdvanceAllBossTurnLimits(): 보스·중간 보스의 EnemyHealthController.RemainingBossTurns를 1 줄임. 0이 된 보스가 있으면 OnGameOver

이동 → 지원 → 타일 → 공격 → 디버프 순서는 20번 1장 [적 1턴의 순서]를 따름. 메서드 위치만 옮겨도 같은 턴에 적용되는지가 달라짐.

[2-3] 적 한 마리 생성

EnemyManager.SpawnWaveRoutine → WaveManager.SpawnWaveEnemies(이번 웨이브 구성 전부)
  → 한 마리마다 TileManager.TryGetRandomEnemySpawnIndex(전체 패스 인덱스 중 무작위. 타일당 수 제한 없음) → EnemyObjectPool2D.Spawn(그 인덱스)
  → 풀에서 꺼내 활성화 → 이전 디버프 정리 → 이동 초기화 (이 안에서 TileManager의 받은 인덱스에 점유 등록) → 체력 초기화
  중간 보스·최종 보스도 웨이브 구성으로 같은 길을 거침.
- 살아 있는 적의 목록은 따로 없음. 원본은 TileManager의 칸별 점유이고, GetAllEnemiesOnPath가 부를 때마다 새 List로 모아 줌.
  EnemyManager는 상태가 없음. 그래서 점유에 등록된 것은 전부 "적"으로 셈: 한도 판정(CheckEnemyLimit), 이동·타일·디버프 순회,
  타워의 타겟 탐색(TowerAttackAction이 GetEnemyOccupantsAtPathIndex), 적 정보 패널의 칸별 목록(GetLivingEnemiesAtPathCell).
- 풀 클래스가 이동·체력·상태 초기화의 순서까지 알고 있음.
- 활성화가 초기화보다 먼저라, OnEnable에서 완성된 데이터를 가정하면 위험.
  권장 순서: 비활성 상태에서 디버프·체력·이동 초기화 → 위치 설정 → 활성화 → 점유 등록. (5장 6-5)
- 풀의 이동·체력 초기화 뒤 큐브의 PlaySpawnDrop을 실행함. SpawnWaveRoutine은 낙하가 전부 끝나야 플레이어 턴으로 넘김.

[2-4] 타워 한 발의 공격과 사망

TowerManager → TowerController.ExecuteTurnAction()
  → TargetAttackAction / SplashAttackAction → TowerAttackAction의 투사체 준비·발사
  → GlobalProjectileManager / ProjectileObjectPool2D → ProjectileHit2D가 이동하여 명중 판정
  → EnemyHealthController.ApplyDamage()
      → 치명타 관련 디버프 반응 → 방어력 등을 반영한 피해 → HP 표시, 대미지 텍스트
      → 사망 시 Die() (m_hasDied로 한 번만 실행)
          → 공격 타워의 처치 반응 (NotifyEnemyKilled)
          → WaveManager.GetKillReward로 보상 계산 → CurrencyManager에 지급
          → WaveManager.OnEnemyDied(적 종류, 소환 웨이브) → 40웨이브에 소환된 Boss면 GameManager.OnGameClear()
          → ReturnToPool(): 디버프·이동·점유 정리, 풀 반환
단일 공격은 ProjectileHit2D에서 TowerController.NotifyPrimaryTargetHit()로도 돌아옴 (스킬의 적중 집계).
스킬이 쏜 투사체(ProjectileStats.skill)는 명중할 때 TowerSkill.OnSkillProjectileImpact만 호출함.

[2-5] 타일 효과의 전달

BuffAction / DebuffAction
  → TileManager: SourceID, 적용 버전, 좌표, 수치 등의 효과 기록 (TowerTileBuffEffect, PathTileDebuffEffect)
      → TowerController: 타워가 받는 버프/스택 적용 (새 틀의 문양은 TowerBuffStatus가 상태를 가짐. 지금은 불만)
      → EnemyDebuffController: 적이 받는 디버프/스택 적용 (새 틀의 문양은 EnemyDebuffRule이 규칙을 가짐. 지금은 불만)
'타일에 기록하고 대상이 읽는 구조'는 원한 방향이고, 존(20번 4-1장)도 이 구조 위에 올림 (5장 3-7 ~ 3-9).

4. 지금 코드와 기획의 차이 (2026-10-14에 코드를 읽어 확인한 것)

이미 되어 있는 것
- 길의 순환: TileManager.WrapPathIndex, EnemyMoveController의 전진·후진이 감아서 돎 (뒤로 가는 하한 없음). 첫 이동은 m_hasMadeFirstMove로 판정.
- 적 수 한도: GameManager.EnemyLimit = 사이클 × 20 (하드 15), CheckEnemyLimit(적 수 > 한도)을 GameManager가 웨이브 시작의 소환 직전에만 부름.
  라이프·방어막·도착 처리는 지웠고 상단에 "적 수/한도"를 보여 줌 (22번 2026-10-14).
- 문양 번호: TowerEmblem 상수와 BuffTarget·DebuffTarget enum에 물이 들어가 있고 원소 순서도 새 번호 (07 불 ~ 14 어둠).
  TowerDataCSV.csv는 280줄 (물 20줄 포함).
  에셋의 칸도 14종이 다 있음: Resources/Projectiles의 101 ~ 114·201 ~ 214, TowerBase.prefab의 문양 스프라이트 14칸,
  DebuffZone.prefab의 심볼 대응표 1 ~ 14 (두 표가 문양마다 같은 그림을 가리킴), TowerCharacterCatalog 3 ~ 14 (검·도끼는 TowerVisual의 레이어 배열).
  그림이 이름과 맞는지와 EffectLibrary의 끊어진 칸 셋은 5장 0-2.
- 불 문양만 새 틀의 초안이 있음 (TowerSkill·TowerBuffStatus·EnemyDebuffRule). 단, 스택을 받는 타워와 적이 가지는 옛 방식.
- 시너지 타워 조합표: TowerManager.s_synergyDefinitions가 이미 20번 9장 [조합표] 14종과 같음 (뇨르드 6014, 스카디·발드르의 새 재료).
  SynergyCharacterCatalog도 6001 ~ 6014가 다 있음. 효과는 없고 생성과 표시만 (5장 5-3).
- 타워 정보 카드의 상당 부분: TowerInfoPanel이 위력·사거리·행동력·공격 횟수(지원은 스택)·치명타·계수·Duration·Mastery를 이미 보여 줌 (5장 3-13).

아직 옛 코드인 것 (큰 것만. 자세한 것은 5장의 각 항목)
- 타일: 길 위 특수 타일이 방어·속도·회복 셋 (5 / 5 / 2개). 타워 쪽은 공격력 ×1.5·행동력 -1·공격 횟수 셋.
- 적: enum은 종류 다섯(Normal, Speed, Depend, MiddleBoss, Boss)이 남아 있음 (웨이브에는 Speed·Depend가 안 나옴). 이동력은 최댓값 하나(1 ~ Speed).
      특성 주사위 없음. 저항력 값은 있으나 쓰지 않음.
      방어력을 0.1 ~ 500으로, 한 번의 피해를 50000으로 자름. 방어력은 음수가 될 수 없음.
- 타워: CSV 열이 SplashRadius·AdditionalHitCount (Mastery·Stack 없음). 문턱은 60 ÷ 레벨. 컬러 강화는 옛 표.
        버프는 사거리 안의 모든 타일에 기록, 디버프 장판은 자유롭게 옮김, 스택은 받는 쪽이 가짐. 타겟 우선순위는 옛 목록(선두·후미).

6. 시스템별 구조 메모
======================================================================

5장에 적은 내용은 반복하지 않음. 여기는 "왜 엮여 있는가"와 분리 방향만.

[읽기 어려운 이유]
파일이 나뉘어 있는 것 자체보다, 한 기능의 시작·종료·데이터 소유자가 흩어져 있기 때문.
A. GameManager가 턴을 진행하지만 종료 대기는 TowerManager와 투사체 관리자에도 있음.
B. 적의 체력 담당이 보상 지급, 승리 통보, 풀 반환, 이동 정리까지 담당.
C. TileManager가 효과를 기록하고 타워/적이 읽지만, 구형 직접 방식의 잔재도 남아 있음.
D. TowerController에 공통 스탯, 구체 공격 생성, 버프, 투사체 연출이 모임.
E. 타입 참조가 거의 없는 파일도 씬 이름·리소스 경로·애니메이션 이벤트에는 강하게 연결됨.

[TowerManager]
- CSV 읽기, 데이터 인덱싱, 글로벌 업그레이드, 생성·판매, 이동·교환, 티어/컬러 강화, 합성, 행동 순서, 시너지, 치트 입력을 모두 담당.
- TowerController가 TowerManager의 공유 강화 상태를 읽거나 갱신하는 역방향도 있음.

[TowerController와 공격 Action]
- 역할 구분 (2026-10-02 확정):
    TowerController     최종 스탯 구조체(TowerStats)를 만들고, 그 스탯으로 행동력을 계산하고, 행동 스크립트와 스킬 스크립트를 부름.
    행동·스킬 스크립트  대상 선택, 투사체 연출, 피해 계산을 각자 알아서 함.
- 위성 투사체 연출은 TowerAttackAction.SatelliteAttackRoutine에 있음. 연출 설정값 5개는 프리팹의 값을 지키려고 TowerController에 남아 있음.
- Splash/Target/Buff/Debuff로 공격 방식(스킬 1)을 나눈 방향은 좋음. 스킬 2는 TowerSkill, 받은 버프는 TowerBuffStatus가 같은 방식으로 나눔.
  TowerController는 TryUseSkill / NotifyPrimaryTargetHit / AdvanceSkillTurn / RefreshStackBuffs / ConsumeBuffAction(받은 버프와 스킬의 OnOwnerActed)만
  부르고 문양을 모르는 것이 목표.
- bool ExecuteAction()만으로는 비동기 공격의 완료를 표현할 수 없어 상위 매니저가 전역 투사체를 감시함 (5장 6-3).

[GameManager]
- 턴 상태, 턴 코루틴, 한도, 게임 속도와 일시정지, 게임오버/클리어를 함께 가짐.
- 상태 클래스(PlayerTurnState 등)가 UIManager, 드래그 취소, DebuffZone 취소, 카메라를 직접 조작.

[WaveManager]
- 웨이브 구성, 난이도 배율, 풀 선택, 소환, 중간 보스, 보상 계산, 최종 클리어 통보를 담당.

[Enemy]
- EnemyHealthController: 수명주기의 허브 (5장 3-12).
- EnemyMoveController: 행동 카운터, 주사위, 이동, 점유, 타일 스탯 적용, 겹친 적의 그리는 순서. 타일 스탯 적용과 이동 자체는 나눌 후보.
- EnemyDebuffController: 스택, 즉시 피해, 지속 피해, 처형, 이동/방어/취약 보정, 이탈 후 처리, duration, UI 문구를 한 클래스가 처리.
  옛 문양은 ApplyZoneStack, AdvanceDebuffTurn, RefreshPersistentStats의 switch를 함께 고쳐야 함. 새 틀은 EnemyDebuffRule 파일 하나 + Get에 한 줄.
- EnemyManager: 상태가 없음. 적은 TileManager의 점유에서 매번 모음 (GetAllEnemiesOnPath. 2장 [2-3]).
  따로 목록을 둘지는 6-13(턴마다 새 List)과 4-13(빛의 더미)을 할 때 정함. 둔다면 등록/해제는 대칭 API로, 밖에는 IReadOnlyList로.

[TileManager]
- 경로·소환 타일 인덱스, 타워/적 점유, 적의 도착 순서와 타일별 적 수 표시, 특수 타일 배치, 타워 버프와 경로 디버프 기록, duration 감소, source별 삭제,
  위성 이펙트 생성/삭제, 좌표 변환, 길의 화살표 발광까지 담당.
- 좌표 판정을 Dictionary로 하는 방향 자체는 기획과 잘 맞으므로 유지. 효과 저장 / 턴 진행 / 연출을 나눌 후보.

[ProjectileHit2D]
- 유도 이동과 회전, 수명과 풀 반환, 단일/스플래시 명중, 얼음 추가 대상, 연쇄, 데미지 전달, 구형 디버프 생성, Trail/Particle 구성,
  원소별 색상을 모두 담당. 명중 시점에 피해가 들어가는 것은 유지하되 시각 수명과 전투 결과 처리를 나눌 후보.
- 공격자 콜백(NotifyPrimaryTargetHit, 스킬 투사체의 OnSkillProjectileImpact)과 대상 사망 재진입에 주의.
- 스킬 투사체는 명중 뒤 후속 코루틴이 끝날 때까지 보이지 않는 채로 남아 있음 (턴 대기가 투사체 수를 세기 때문).

[UI]
- UIManager는 패널 켜고 끄기만. 화면별 파일: PlayerTurnPanel, GameInfoPanel, TowerInfoPanel, TileinfoPanel, EnemyInfoPanel,
  OptionPanel, GameOverPanel, GameClearPanel.

- EnemyListItemUI는 패널을 직접 알지 않고 선택 콜백을 받음.
