2. 실제 실행 흐름                                       [24-2] + 25 반영
======================================================================

[2-1] 게임 시작과 한 웨이브

GameManager.OnStartGame()
  → Idle 상태, 기존 turnRoutine 중지
  → TurnLoopRoutine()
      → PlayerTurnRoutine(): Player 상태, 턴 종료 버튼 대기
      → EnemyWaveRoutine(): EnemyTurnRoutine 10번, 처음 5번만 shouldSpawn=true
          → 40웨이브면 최종 보스가 살아 있는 동안 EnemyTurnRoutine(false)를 계속 반복
          → 종료 상태가 아니면 WaveManager.NextWave()
          → 완료 웨이브 번호로 대지 타워 웨이브 처리
      → 다시 플레이어 턴

- turnRoutine은 '누구 턴인가'가 아니라 실행 중인 코루틴 핸들.
- EnemyTurnRoutine 끝의 WaitForSeconds(0.3f)가 남아 있음 (코드 확인). 초 단위 대기가 전부 없어진 상태는 아님.
- NextWave()는 완료한 웨이브가 40 미만일 때만 호출됨. 웨이브 번호는 40에서 멈춤.
  40웨이브는 10턴 뒤에도 플레이어 턴으로 돌아가지 않고 보스가 죽거나 도착할 때까지 적 턴을 계속함 (A-5).

[2-2] 적 1턴 — GameManager.EnemyTurnRoutine()

  ① ProcessEnemyMovement()
      → EnemyManager.ProcessEnemyTurnRoutine()
          → 소환 턴이면 WaveManager.SpawnWaveEnemiesForTurn()
          → 적마다 EnemyMoveController.ProcessTurnMoveRoutine(), 모든 이동 완료 대기
  ② ProcessTowerSupport()
      → TowerManager.BeginEnemyTurnForTowers(): 이전 타일 버프 기록, 타워 상태 시간 감소
          (타워마다 AdvanceStackBuffTurn → AdvanceSkillTurn)
      → ExecuteSupportTowerActionTurnRoutine(): 버프/디버프 타워 실행,
          그 뒤 타워가 자기 타일의 스택형 버프 기록을 읽음 (RefreshStackBuffs)
  ③ ProcessTileBuffs()
      → EnemyManager.ApplyAllTileBuffs()
          → 적마다 EnemyMoveController.CheckAndApplyTileBuff()
              → 기존 타일 스탯 초기화 → 도착 타일의 속도/방어/회복 적용
              → EnemyDebuffController.RefreshTileDebuffs()
  ④ ProcessTowerAttacks()
      → TowerManager.ExecuteAttackTowerActionTurnRoutine()
          → 타워별 스킬 확인(TryUseSkill) → 타워 기본 행동 → 활성 투사체가 없어질 때까지 대기
      → GameManager의 추가 투사체 완료 확인
  ⑤ ProcessDamageDebuffs()
      → EnemyManager.AdvanceAllDebuffTurns()
          → 적마다 EnemyDebuffController.AdvanceDebuffTurn(): 상태 시간, 도트 피해, 조건부 즉사

이 순서는 게임 규칙입니다. 메서드 위치만 옮겨도 같은 턴 적용 여부가 달라집니다.

[2-3] 적 한 마리 생성

EnemyManager → WaveManager(이번 턴에 무엇을 몇 마리) → EnemyObjectPool2D.Spawn()
  → 풀에서 꺼내 활성화 → 이전 디버프 정리 → 이동 초기화와 점유 등록
  → EnemyManager에 등록 → 체력 초기화

- 풀 클래스가 이동·체력·상태 초기화와 전역 등록 순서까지 알고 있음.
- 활성화가 초기화보다 먼저라, OnEnable에서 완성된 데이터를 가정하면 위험 [23-4-6][24-3-14].
  권장 순서: 비활성 상태에서 디버프·체력·이동 초기화 → 위치 설정 → 활성화 → 점유와 EnemyManager 등록.

[2-4] 타워 한 발의 공격과 사망

TowerManager → TowerController.ExecuteTurnAction()
  → TargetAttackAction / SplashAttackAction → TowerAttackAction의 투사체 준비·발사
  → GlobalProjectileManager / ProjectileObjectPool2D
  → ProjectileHit2D가 이동하여 명중 판정
  → EnemyHealthController.ApplyDamage()
      → 치명타 관련 디버프 반응 → 방어력 등을 반영한 피해 → HP 표시, 대미지 텍스트
      → 사망 시 Die() (m_hasDied로 한 번만 실행)
          → 공격 타워의 처치 반응 (NotifyEnemyKilled)
          → WaveManager.GetKillReward로 보상 계산 → CurrencyManager에 지급
          → WaveManager.OnEnemyDied(적 종류, 소환 웨이브)
              → 40웨이브에 소환된 Boss면 GameManager.OnGameClear()
          → ReturnToPool(): 디버프·이동·점유 정리, 풀 반환

단일 공격은 ProjectileHit2D에서 TowerController.NotifyPrimaryTargetHit()로도 돌아옵니다 (스킬의 적중 집계).
스킬이 쏜 투사체(ProjectileStats.skill)는 명중할 때 TowerSkill.OnSkillProjectileImpact만 호출합니다.
'피해 처리 하나'를 따라가면 타워·재화·웨이브·게임 종료까지 보이는 구조입니다.

[2-5] 타일 효과의 전달

BuffAction / DebuffAction
  → TileManager: SourceID, 적용 버전, 좌표, 수치 등의 효과 기록
      → TowerController: 타워가 받는 버프/스택 적용 (새 틀의 문양은 TowerBuffStatus가 상태를 가짐)
      → EnemyDebuffController: 적이 받는 디버프/스택 적용 (새 틀의 문양은 EnemyDebuffRule이 규칙을 가짐)
타일 기록에는 Power와 StackGain(한 번에 쌓는 스택 수)도 들어 있습니다.

'타일에 기록하고 대상이 읽는 구조'는 원한 방향입니다. 다만 중복 적용 방지, 소스 제거,
지속 시간, 스택 갱신 시점이 함께 맞아야 해서 세 영역 사이의 실행 순서 결합이 큽니다.

A-1. 타겟 타워 탄 사전 분배 + 공격 단위 완료 추적     [문답 18][24-3-4][23-4-10]
  [수정함 2026-10-02 · 컴파일·실행 확인 전]
    - 탄 사전 분배: 단일 타워는 탄마다 대상을 다시 고름. 발사할 때 그 탄이 깎을 체력을 대상에
      예약하고(EnemyHealthController.ReserveDamage), 예약만으로 죽을 적은 다음 탄이 건너뜀.
      사거리의 적이 전부 죽을 예정이면 남는 탄은 원래 우선순위의 적에게 그대로 쏨.
      예상 피해는 EstimateDamage(방어력·방어 관통·취약·고정 피해 전환). ApplyDamage도 같은 식을 씀.
      치명타는 발사 전에 탄마다 굴림 (확정, 원래 코드도 그랬음).
      예상에 들어가지 않는 것: 전기 추가 타격, 얼음 추가 타격, 빛 연쇄, 창 디버프의 치명타 즉사.
    - 활성 투사체 수: 씬 전체 검색(FindObjectsByType)을 없앰. 투사체가 켜지고 꺼질 때 스스로
      등록하는 목록(ProjectileHit2D.ActiveCount)을 셈.
    - 타워별 대기: TowerController.IsAttackInProgress(위성을 만들고 쏘는 중)와 남은 투사체 수로 판단.
      투사체 수가 5초(TowerManager의 m_attackStallTimeout) 동안 변하지 않으면 경고 로그를 남기고
      다음 타워로 넘어감. 안쪽 대기에도 타임아웃이 생김.
    - 투사체 수명: 기본 1.5초 고정에서 "날아갈 거리 ÷ 속도 + 0.5초"(최소 1.5초)로.
    남은 것: 대기 완료·취소·타깃 소멸·풀 반환을 하나의 종료 약속으로 묶는 것 (지금은 여전히
            전체 투사체 수 기준. 공격마다 자기 탄 목록을 드는 구조는 아님), 광역 타워의 분배.
    확인: 체력이 낮은 적 여럿에게 탄 수가 많은 단일 타워를 쏘면 탄이 나뉘어 가는지.
          턴이 멈추지 않는지, 경고 로그 "타워 공격이 … 끝나지 않아"가 뜨지 않는지.
  내용: 발사 전에 "이 탄이 누구에게 가서 얼마를 깎는지"를 미리 계산.
        A가 4발에 죽으면 5번째 탄부터는 다음 타겟팅 순서의 적에게 배정.
  함께 하는 이유: 탄을 미리 배정하려면 "이번 공격이 쏜 탄 목록"을 들고 있어야 하고,
        그 목록이 곧 "해결되지 않은 공격의 명시적 추적"이 됨.
        지금은 GlobalProjectileManager.GetActiveProjectileCount()가 FindObjectsByType로 씬의
        활성 투사체 전체를 매 프레임 검색해서 0이 될 때까지 무한 대기함 (코드 확인).
        반환되지 않은 투사체 하나가 턴 전체를 멈출 수 있고, 준비된 위성형 투사체도 집계될 수 있음.
  대상: TargetAttackAction, TowerController(위성 발사 코루틴), TowerManager(대기 루프),
        GlobalProjectileManager, GameManager(바깥 타임아웃).
  주의: 예상 피해 계산에 방어력·취약·치명타·고정 피해 전환이 들어가야 함.
        치명타를 발사 전에 굴릴지 명중 때 굴릴지 정해야 함 (10장 5번).
        가장 안쪽 대기에도 타임아웃이 필요 (지금은 바깥에만 있어서 도달하지 못할 수 있음).
        대기 완료·취소·타깃 소멸·풀 반환을 같은 종료 약속으로 연결.
        투사체 기본 lifeTime 1.5초는 거리/속도 기반으로 계산 [23-4-10].

[읽기 어려운 이유]                                                    [24-1]
파일이 나뉘어 있는 것 자체보다, 한 기능의 시작·종료·데이터 소유자가 흩어져 있기 때문.
A. GameManager가 턴을 진행하지만 종료 대기는 TowerManager와 투사체 관리자에도 있음.
B. 적의 체력 담당이 보상 지급, 승리 통보, 풀 반환, 이동 정리까지 담당.
C. TileManager가 효과를 기록하고 타워/적이 읽지만, 구형 직접 방식의 잔재도 남아 있음.
D. TowerController에 공통 스탯, 구체 공격 생성, 버프, 투사체 연출이 모임.
   (불 스킬과 불 버프 상태는 2026-10-02에 TowerSkill / TowerBuffStatus로 나감)
E. 타입 참조가 거의 없는 파일도 씬 이름·리소스 경로·애니메이션 이벤트에는 강하게 연결됨.

[TowerManager]
- CSV 읽기, 데이터 인덱싱, 글로벌 업그레이드, 생성·판매, 이동·교환, 티어/컬러 강화, 합성,
  행동 순서, 대지 타워 웨이브 기능, Darkness 공유 수치, 시너지, 치트 입력을 모두 담당.
- TowerController가 TowerManager의 공유 강화 상태를 읽거나 갱신하는 역방향도 있음.
- 분리 순서는 F-1 → F-3.

[TowerController와 공격 Action]
- 역할 구분 (2026-10-02 확정):
    TowerController  최종 스탯 구조체(TowerStats)를 만들고, 그 스탯으로 행동력을 계산하고,
                     행동 스크립트(TowerAttackAction 계열)와 스킬 스크립트(TowerSkill 계열)를 부름.
    행동·스킬 스크립트  대상 선택, 투사체 연출, 피해 계산을 각자 알아서 함.
  [반영 2026-10-02 · 컴파일·실행 확인 전] 위성 투사체 연출(띄우기·발사 순서·배치 좌표)을
    TowerController에서 TowerAttackAction.SatelliteAttackRoutine으로 옮김. 연출 설정값 5개는
    타워 프리팹의 값을 지키려고 TowerController에 남기고 ProjectileSatelliteSettings로 넘김.
    옛 직접 버프 삭제(C-3)와 합쳐 TowerController는 885줄 → 약 495줄.
  아직 TowerController에 남은 "스탯 만들기 이외"의 것: 12개 문양의 타일 버프 switch(스탯 만들기의 일부),
    선택·사거리 표시, 디버프 장판 연결, 어둠 처치 집계(NotifyEnemyKilled).
- 구체 공격 클래스를 직접 new로 생성하고 최종 스탯을 관리.
- Splash/Target/Buff/Debuff로 공격 방식(스킬 1)을 나눈 방향은 좋음.
  스킬 2는 TowerSkill, 받은 스택형 버프는 TowerBuffStatus가 같은 방식으로 나눔 (지금은 불만).

  RefreshStackBuffs / AdvanceStackBuffTurn 만 호출하고 문양을 모름.

[11-1] 수동 확인 — 현재 규칙 기준                                    [25-7]

- 한 웨이브 10턴, 첫 5턴만 소환.
- 소환된 적이 그 턴에 1번 타일로 이동.
- 이동 완료 → 지원/타일 → 공격 명중 완료 → 도트 순서.
- 사거리에 적이 없던 타워가 적이 들어온 턴에 바로 공격.
- 치명타에 활 버프의 거리 보너스가 반영.
- 방어 타일 위에서 해머 디버프를 받으면 +20%와 감소가 합산.
- 회복 타일에서 매 턴 최대 체력 5% 회복 (한 턴에 한 번만).
- 0번·마지막 타일로 장판을 드래그하면 놓이지 않음. 새 디버프 타워의 첫 장판도 그 칸을 피함.
- 3~4티어 장판은 행동당 2스택, 5티어는 5스택. (불 제외. 불은 AttackCount 만큼)
- 일반 적 처치 골드가 웨이브에 비례 (1웨이브 10, 11웨이브 110).
- 보스 처치 보상: 10웨이브 1000골드 20젬, 20웨이브 4000골드 80젬.
