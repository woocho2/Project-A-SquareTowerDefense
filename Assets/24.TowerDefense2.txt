24. TowerDefense2 — 전체 스크립트 결합도와 호출 흐름 점검
작성일: 2026-09-23
대상: 현재 작업 폴더에 실제로 저장된 코드. 이전 대화의 계획이 아니라 현재 구현을 기준으로 함.
목적: 코드를 어디서부터 읽어야 하는지, 무엇을 바꾸면 어디에 영향이 가는지 파악하기.
작업 범위: 분석 및 이 문서 작성만 수행. C#·프리팹·씬·CSV는 수정하지 않음.

======================================================================
0. 이 문서를 읽는 방법 / 조사 범위
======================================================================

처음부터 부록까지 전부 읽을 필요는 없습니다.
1) 1장의 핵심 요약 → 2장의 실제 턴 순서부터 읽습니다.
2) 이해하려는 기능이 생기면 3장의 결합 사례를 봅니다.
3) 특정 파일을 수정하기 직전에는 7장의 해당 파일 항목을 찾습니다.
4) 부록의 '들어오는 참조'는 함께 점검할 후보입니다. 모두 실행되는 호출자는 아닙니다.

검사한 자체 C# 파일: 총 69개.
- Assets/3. Scripts: 61개. 이 안에 CSV 에디터 임포터 1개가 포함됨.
- Assets/Editor: 8개.
- DOTween 등 외부 플러그인 구현과 Unity/패키지 내부는 파일별 감사 대상에서 제외.
  단, 자체 코드가 엔진·플러그인·씬·프리팹에 의존하는 부분은 포함.
- .unity/.prefab/.asset의 스크립트 GUID 참조, 애니메이션 이벤트도 보조 확인.

검증 수준:
- 현재 소스의 정적 분석 및 주요 실행 흐름 수동 추적.
- Unity 실행, 실제 장면의 전체 오브젝트 상태, 플레이 테스트는 수행하지 않음.
- '확인 사실'과 '실행 조건에 따라 발생 가능한 위험'을 구분함.
- 파일별 참조 수는 주석·문자열을 제외한 자체 타입 이름 참조를 파일 단위로 집계한 값.
  변수의 실제 호출 대상, 리플렉션, Unity 직렬화 전체를 해석한 C# 컴파일러 결과는 아님.
- 같은 파일의 enum/struct만 사용해도 그 파일을 참조한 것으로 집계됨.
  따라서 참조 수를 결합도의 점수나 버그 수로 읽으면 안 됨.
- 본문 및 부록의 줄 번호는 작성 시점 기준. 코드 수정 후에는 메서드 이름으로 검색할 것.

용어:
- 나가는 참조: 이 파일이 알고 있는 다른 파일.
- 들어오는 참조: 이 파일의 타입을 알고 있는 다른 파일.
- 강한 결합: 상대의 구체 구현·전역 상태·내부 순서까지 알아야 제대로 동작.
- 중간 결합: 구체 타입/공유 데이터에 연결되지만 역할 경계가 비교적 분명.
- 약한 결합: 단순 값·인터페이스·콜백 등 제한된 약속만 공유.
- 숨은 결합: 코드 호출 대신 오브젝트 이름, 배열 순서, CSV 열, 실행 시점 등에 의존.
- 순환 참조: 서로의 타입을 알고 있는 구조. 무한 재귀를 뜻하는 것은 아님.

======================================================================
1. 결론: '파일이 나뉘어 있음'과 '역할이 분리되어 있음'은 다릅니다
======================================================================

현재 읽기 어려운 이유는 하나의 기능이 여러 파일로 분리된 것 자체보다,
그 기능의 시작·종료·데이터 소유자가 서로 다른 곳에 분산되어 있기 때문입니다.

특히 아래가 동시에 존재합니다.
A. GameManager가 턴을 진행하지만, 종료 대기는 TowerManager와 투사체 관리자에도 있음.
B. 적의 체력 담당이 보상, 승리 판정 통보, 풀 반환, 이동 정리까지 담당.
C. TileManager가 상태 전달 데이터를 관리하고, 타워/적이 읽지만,
   동시에 각 대상이 자기 스탯을 직접 덮어쓰는 예전 방식도 남아 있음.
D. UI가 상태를 표시하는 동시에 생명 감소 표현과 게임오버 흐름도 일부 판단.
E. TowerController에 공통 스탯, 구체 공격 생성, 불 스킬, 버프, 투사체 연출이 모임.
F. 타입 참조가 거의 없는 파일도 씬 이름·리소스 경로·애니메이션 이벤트에는 강하게 연결됨.

우선 읽을 중심 파일:
- GameManager: 한 턴의 큰 순서.
- TowerManager: 타워 전체 작업, 데이터, 경제/합성/시너지/행동 순서.
- TowerController: 타워 1개의 실제 행동과 최종 스탯.
- EnemyHealthController: 피해→사망→보상→클리어 통보→반환.
- EnemyMoveController / EnemyDebuffController: 이동 규칙과 상태 변화.
- TileManager / TilePath: '칸의 효과'와 '길/점유 정보'라는 서로 다른 책임.
- UIManager: 화면 표시 외에도 게임 흐름으로 되돌아가는 연결이 많은 곳.

좋은 분리도 있습니다.
- DamageText는 구체 DamageTextPool 대신 IObjectPool을 받아 반환함.
- EnemyListItemUI는 패널을 직접 알지 않고 선택 콜백을 받음.
- CurrencyManager의 변경 이벤트로 UI가 갱신됨.
- EnemyUIController → HPBarSlider는 목적이 좁은 연결.
이런 연결까지 전부 이벤트나 인터페이스로 바꿀 필요는 없습니다.

2. 실제 실행 흐름: 위에서 아래로 따라 읽는 길
======================================================================

[2-1] 게임 시작과 한 웨이브

GameManager.OnStartGame() [93]
  → Idle 상태로 변경
  → 기존 turnRoutine이 있으면 중지
  → TurnLoopRoutine() [103]
      → PlayerTurnRoutine() [144]
          → Player 상태
          → 턴 종료 버튼 입력을 기다림
      → EnemyWaveRoutine() [114]
          → 10번 EnemyTurnRoutine 실행
          → 처음 5번만 shouldSpawn=true
          → 종료 상태가 아니면 NextWave()
          → 완료 웨이브 번호로 대지 타워 웨이브 처리
      → 다시 플레이어 턴

주의:
- turnRoutine은 '누구 턴인가' 값이 아니라 실행 중인 코루틴을 가리키는 핸들입니다.
- 현재 코드에서는 적 1턴마다 플레이어 턴이 오는 것이 아니라 10턴 후에 옵니다.
- GameManager[187]의 '다음 루프에서 자동으로 플레이어 턴' 주석은 현재 웨이브
  반복 구조를 충분히 설명하지 못합니다.
- EnemyTurnRoutine 끝에 WaitForSeconds(0.3f)[188]가 현재 남아 있습니다.
  흐름은 완료 대기를 사용하지만 모든 초 단위 대기가 제거된 상태는 아닙니다.

[2-2] 적 1턴

GameManager.EnemyTurnRoutine() [171]
  ① ProcessEnemyMovement()
      → EnemyManager.ProcessEnemyTurnRoutine()
          → 필요할 때 WaveManager.SpawnWaveEnemiesForTurn()
          → 적마다 EnemyMoveController.ProcessTurnMoveRoutine()
          → 모든 이동 완료 대기

  ② ProcessTowerSupport()
      → TowerManager.BeginEnemyTurnForTowers()
          → 이전 타일 버프 기록 및 타워 상태 시간 감소
      → ExecuteSupportTowerActionTurnRoutine()
          → 버프/디버프 타워 실행
          → 모든 타워가 불 버프 타일 기록을 읽음

  ③ ProcessTileBuffs()
      → EnemyManager.ApplyAllTileBuffs()
          → 적마다 EnemyMoveController.CheckAndApplyTileBuff()
              → 기존 타일 스탯 초기화
              → 도착 타일의 속도/방어/회복 적용
              → EnemyDebuffController.RefreshTileDebuffs()

  ④ ProcessTowerAttacks()
      → TowerManager.ExecuteAttackTowerActionTurnRoutine()
          → 타워별 불 메테오 확인
          → 타워 기본 행동
          → 활성 투사체가 없어질 때까지 대기
      → GameManager의 추가 투사체 완료 확인

  ⑤ ProcessDamageDebuffs()
      → EnemyManager.AdvanceAllDebuffTurns()
          → 적마다 EnemyDebuffController.AdvanceDebuffTurn()
              → 상태 시간/도트 피해/조건부 즉사 처리

핵심: 지원 타워 실행 → 타일 읽기 → 공격 → 도트라는 순서는 게임 규칙입니다.
단순히 메서드 위치를 옮기는 것만으로도 같은 턴 적용 여부가 달라집니다.

[2-3] 적 한 마리 생성

EnemyManager
  → WaveManager: 이번 턴에 무엇을 몇 마리 만들지 결정
  → EnemyObjectPool2D.Spawn()
      → 풀에서 객체 꺼내기 및 활성화
      → 이전 디버프 정리
      → 이동 초기화 / TilePath 등록
      → EnemyManager에 적 등록
      → 체력 초기화

읽다가 EnemyManager로 다시 돌아오는 이유:
소환을 요청한 관리자가 '생성된 적 목록'도 가지고 있기 때문입니다.
이 경로 자체는 끝나는 등록 흐름이지 무한 반복 호출이 아닙니다.
다만 풀 클래스가 이동·체력·상태 초기화와 전역 등록 순서까지 알고 있다는 결합이 있습니다.

[2-4] 타워 한 발의 공격과 사망

TowerManager
  → TowerController.ExecuteTurnAction()
  → TargetAttackAction / SplashAttackAction
  → TowerAttackAction의 투사체 준비/발사 경로
  → GlobalProjectileManager / ProjectileObjectPool2D
  → ProjectileHit2D가 이동하여 명중 판정
  → EnemyHealthController.ApplyDamage()
      → 치명타 관련 디버프 반응
      → 방어력 등을 반영한 피해
      → HP 표시 / 대미지 텍스트
      → 사망 시 Die()
          → 공격 타워의 처치 반응
          → CurrencyManager에 보상
          → WaveManager에 사망 통보
              → 조건을 만족하면 GameManager.OnGameClear()
          → 상태/이동/점유 정리
          → 풀 반환

불 타겟 공격은 ProjectileHit2D에서 TowerController.NotifyFireTargetHit()로도 돌아옵니다.
따라서 '피해 처리 하나'를 따라가면 타워·재화·웨이브·게임 종료까지 보이는 구조입니다.

[2-5] 타일 효과의 전달

BuffAction / DebuffAction
  → TileManager: SourceID, 적용 버전, 좌표, 수치 등의 효과 기록
      → TowerController: 타워가 받는 버프/스택 적용
      → EnemyDebuffController: 적이 받는 디버프/스택 적용

소유권을 구분해서 읽어야 합니다.
- TilePath: 길의 순서와 적의 위치/점유.
- TileManager: 그 위치에 전달할 효과 데이터.
- TowerController / EnemyDebuffController: 각 대상에게 이미 적용된 상태와 스택.

방향 자체는 사용자가 원한 '타일에 기록하고 대상이 읽는 구조'입니다.
하지만 중복 적용 방지, 소스 제거, 지속 시간, 스택 갱신 시점까지 함께 맞아야 하므로
지금은 세 영역 사이에 실행 순서 결합이 큽니다.

======================================================================
3. 강하게 결합된 부분: 근거 / 영향 / 분리 방향
======================================================================

[3-1] GameManager ↔ GameTurnState ↔ UIManager / 입력
강도: 높음. 실제 동작·상태·화면을 양방향으로 연결.

확인:
- GameManager가 구체 PlayerTurnState/EnemyTurnState 등을 생성.
- 상태 클래스가 UIManager, 드래그 취소, DebuffZone 취소, 카메라를 직접 조작.
- UIManager도 GameManager를 호출.
- UIManager.OnPlayerHit()[1520]가 자체 생명 아이콘 인덱스로 게임오버 화면을 결정.
- GameManager.DecreaseLife()[306]도 실제 생명과 게임오버 상태를 관리.
- UIManager.ShowGameOver()[1544]는 적 HP바를 숨기고 OnPauseGame()을 호출.
  GameManager의 GameOver 상태 전환과 같은 일은 아님.

영향:
생명 판정과 화면 판정이 다른 경로로 움직일 수 있습니다.
표시 코드 변경이 게임 흐름에 영향을 주며, 보스 도착 등의 예외를 따라가기 어렵습니다.

권장:
GameManager가 생명/종료의 원본 값을 소유하고, UI는 그 결과만 표시.
상태 클래스는 턴의 허용 행동/진입·종료를 담당하되 화면 배치는 UI에 맡김.
이때 모든 호출을 이벤트화할 필요는 없고 '표시 → 게임오버 재판정' 역방향부터 제거.

[3-2] TowerManager ↔ TowerController ↔ 공격 클래스
강도: 매우 높음. 여러 기능이 한 연결망에 포함됨.

확인:
- TowerManager는 CSV 읽기, 타워 생성, 비용, 배치, 판매, 합성, 강화, 시너지,
  대지 타워 웨이브 효과, 공격 순서까지 담당.
- TowerController는 구체 공격 클래스를 직접 new로 생성하고, 최종 스탯과 불 상태도 관리.
- TowerController가 TowerManager의 공유 강화 상태를 읽거나 갱신하는 역방향도 존재.
- TowerStats가 TowerController.cs 안에 선언되어 다른 계층도 컨트롤러 파일에 연결됨.
- TowerData.ToTowerStats()는 공격 기반 클래스의 거리 변환 도우미에도 의존.

영향:
새 스킬이나 강화 규칙 하나를 넣어도 관리자·개별 타워·데이터·투사체까지 수정 후보가 됨.
'공통 데이터 참조'와 '행동 책임 참조'가 같은 파일에 섞여 추적이 어렵습니다.

권장 분리 순서:
① TowerStats/enum 같은 순수 데이터부터 별도 파일로 분리.
② CSV 로딩과 조회를 TowerDataCatalog 같은 데이터 전담 역할로 분리.
③ 비용/강화/합성 규칙을 독립 계산 함수로 분리.
④ 이후 타워 행동 실행과 배치 관리 분리.
처음부터 모든 것을 새 매니저로 쪼개면 오히려 이동할 파일만 늘어납니다.

[3-3] 불 스킬이 공통 코드에 직접 박힌 연결
강도: 높음. 새 문양을 추가할 때 같은 결합이 반복될 가능성.

확인:
- TowerManager.ExecuteAttackTowerActionTurnRoutine()[438]이 TryTriggerFireMeteor() 호출.
- TowerController.TryTriggerFireMeteor()[559]는 구체 SplashAttackAction을 사용.
- ProjectileStats에 ownerTower, 불 메테오 여부가 있음.
- ProjectileHit2D의 피해 경로가 화상/연소 배율을 조회하고 타워의 불 적중 함수 호출.
- EnemyDebuffController도 불 상태 배율을 별도 메서드로 노출.

영향:
불은 작동 흐름을 이해하기 위한 첫 구현이지만, 이 형태로 원소를 계속 추가하면
공통 클래스에 원소별 if/switch와 전용 함수가 계속 증가합니다.
최근 추가된 불 코드도 분리 검토 대상이며 예외로 볼 수 없습니다.

권장:
공격 요청에 '피해 정보 + 명중 결과 통보'를 전달하고,
불 스킬이 그 결과를 받아 자기 카운터를 처리하도록 책임 분리.

SceneLoader.StartLoad()는 현재 다음 씬 이름 설정만 하고 실제 LoadScene 줄은 주석 상태.
따라서 이 메서드 호출만으로 씬이 바뀐다고 가정하면 안 됩니다.
여러 이동 방식과 로딩 씬 진입 조건을 한 표준 경로로 정리할 필요가 있습니다.

[프리팹 / 이름 / 에디터]
- WaveManager 스크립트가 붙는 프리팹 이름은 SpawnManager인 자료가 확인됨.
  파일명과 역할명이 다르면 탐색할 때 혼동을 줌.
- DebuffAction / DebuffZone의 Tilemap_Path 이름 검색.
- Resources 투사체 ID 파일명.
- UIStageTheme의 자식 이름 및 스프라이트 이름.
- TilePathEditor가 pathGridPositions를 직접 추가/삭제/초기화.
  경로 인덱스를 저장해 둔 데이터는 경로 편집과 함께 검토해야 함.
- DOTween, TMP, Unity UI, Tilemap, Unity ObjectPool은 외부 계약.
  자체 코드 참조 수에는 포함하지 않았지만 패키지/컴포넌트 제거 시 영향이 있음.

[경로 인덱스와 좌표]
길의 순서 인덱스와 Vector3Int 셀 좌표는 같은 개념이 아닙니다.
현재 일부 범위 조회는 좌표 HashSet으로 중복 제거하고,
좌표→인덱스 조회는 첫 위치를 찾습니다.
나중에 같은 좌표를 다시 방문하는 순환/분기 경로를 만들 때에는 별도 점검이 필요합니다.

[공유 데이터]
IReadOnlyList로 반환해도 그 안의 효과 객체가 수정 가능한 참조형이면
다른 코드가 항목 내부를 바꾸는 것까지 막아주지는 않습니다.
TileManager 효과 기록의 읽기 계약을 확실히 하려면 값 스냅샷/읽기 전용 항목도 검토.

5. 어떤 순서로 리팩토링할지
======================================================================

0단계: 현재 동작을 고정할 최소 확인 목록부터 작성
- 한 웨이브 10턴, 첫 5턴 소환.
- 이동 완료 → 지원/타일 → 공격 명중 완료 → 도트.
- 사망 보상/풀 반환은 1회.
- 일반/중간/최종보스의 종료 조건은 서로 구분.
- 소환 직후, 이동 중 사망, 공격 도중 대상 사망, 게임 종료 시 중단.
- 장판 이동/판매/합성 후 기존 효과 정리.
- 방어 타일 + 방어 디버프 동시 적용.
- 불 버프 스택 누적/소모/만료.
이것이 없으면 파일을 예쁘게 나눠도 동작이 바뀐 것을 발견하기 어렵습니다.

1단계: 혼동을 만드는 거짓 연결 제거 계획
- AddDebuff / SetSpeedMultiplier 빈 메서드의 호출 의도 확인.
- 신형/구형 타워 턴 진입점을 하나로 수렴.
  현재 GameManager는 지원/공격 분리 경로를 사용하지만
  TowerManager.ExecuteTowerActionTurnRoutine이라는 구형 통합 경로도 남아 있음.
- 실행 흐름과 어긋난 주석 수정.
이 단계에서도 사용 여부를 확인하기 전 삭제하지 않습니다.

2단계: 게임 결과가 틀어질 수 있는 책임 정리
- 사망 중복 방지와 최종보스 식별.
- 생명/종료 판정의 단일 소유자.
- 실제 투사체 완료 대기 위치의 안전성.
- 타일/디버프 스탯의 합성 규칙.

3단계: 순수 데이터와 계산 분리
- TowerStats, 효과 기록, enum 등은 동작 컴포넌트와 분리.
- 거리/셀 범위 변환은 TowerAttackAction이 아니라 공용 격자 계산 역할로.
  TilePath도 현재 TowerAttackAction.ToTileRange를 호출하므로 역방향 결합이 있음.
- CSV 조회, 비용, 강화 계산을 가능한 한 입력→출력이 분명한 함수로 분리.

4단계: 큰 관리자 책임을 순서대로 축소
- TowerManager: 데이터 → 경제/강화 → 배치 → 턴 실행 순으로 경계 검토.
- UIManager: 화면 단위로 분리. UI가 게임 결과를 다시 결정하지 않게 함.
- EnemyObjectPool: 저장/반환과 적 초기화 절차를 구분.
새 클래스 이름보다 '원본 데이터를 누가 가진다'를 먼저 결정합니다.

5단계: 불을 기준으로 스킬 확장점 설계
- 타일에 기록할 효과 / 대상이 소유할 상태 / 명중 시 반응을 구분.
- 불 전용 분기를 공통 관리자와 투사체에서 줄임.
- 나머지 문양은 불의 스택 예제 테스트가 통과한 뒤 같은 계약으로 추가.

굳이 하지 않아도 되는 것:
- 모든 메서드를 이벤트로 바꾸기.
- 모든 클래스에 인터페이스 추가하기.
- 직접 연결을 전부 금지하기.
- GameManager에 모든 로직을 합치기.
호출 순서는 명시적으로, 결과 알림은 필요할 때 이벤트로 나누는 편이 읽기 쉽습니다.

9. 참고 지표와 읽기 주의사항
======================================================================

나가는 직접 타입 참조가 많은 파일 (에디터 포함 전체 조사 기준):

- ProjectileHit2D.cs: 나감 11, 들어옴 8
- EnemyHealthController.cs: 나감 9, 들어옴 24
- TowerAttackAction.cs: 나감 8, 들어옴 9
- EnemyInfoPanelUI.cs: 나감 8, 들어옴 2
- TowerManager.cs: 나감 7, 들어옴 8
- DebuffAction.cs: 나감 7, 들어옴 1
- SplashAttackAction.cs: 나감 7, 들어옴 1
- EnemyMoveController.cs: 나감 7, 들어옴 21
- GameManager.cs: 나감 7, 들어옴 8
- BuffAction.cs: 나감 6, 들어옴 1

이 수치는 상대 파일의 enum 하나만 사용해도 1로 셉니다.
예: TowerDataSO.cs의 참조가 많은 것은 공용 enum이 함께 정의되어 있는 영향도 큽니다.
따라서 수치가 큰 순서로 무조건 파일을 쪼개면 안 됩니다.

타입 참조 그래프에서 32개 파일이 하나의 상호 도달 가능한 묶음으로 연결됩니다.
즉 몇 단계를 거치면 시작 파일로 돌아오는 연결 경로가 많다는 뜻입니다.
하지만 struct/enum/상속 참조까지 포함한 결과이므로
'32개가 재귀 호출한다' 또는 '32개 전부를 동시에 고쳐야 한다'는 뜻은 아닙니다.
실제 위험은 3장에 기록한 상태 소유권과 호출·실행 순서로 판단해야 합니다.

리팩토링할 때 각 함수 옆에서 확인할 5가지:
1. 누가 호출하는가?
2. 어떤 값을 읽는가?
3. 어떤 값을 바꾸는가? 그 값의 진짜 주인은 누구인가?
4. 끝났다는 것은 어떻게 알리는가?
5. 대상이 죽거나 씬이 바뀌면 누가 취소/해제하는가?

호출이 여러 파일로 이어지는 것은 정상입니다.
문제는 그 연결의 목적과 데이터 소유권이 보이지 않는 것입니다.
첫 목표는 파일 수를 줄이거나 늘리는 것이 아니라,
'이 기능은 여기서 시작해서 이 결과를 만들고 여기서 끝난다'를 명확히 하는 것입니다.

작성 완료: 자체 스크립트 69개 모두 개별 항목 수록.
코드 수정 없음. 실행 검증이 필요한 위험은 테스트 전 확정 버그로 단정하지 않았습니다.
