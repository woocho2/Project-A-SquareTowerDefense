1프로젝트 개요

북유럽 신화 세계관의 턴제 순환형 타워 디펜스. 적이 지나가는 길은 부루마블처럼 끝없이 도는 고리이고, 도착점과 라이프가 없습니다. 대신 판 위에 남은 적의 수가 한도를 넘으면 패배합니다. 플레이어는 상점에서 타워 카드를 사고, 같은 타워 3기를 모아 자동 합성하며, 버프·디버프 타워의 존(zone)을 배치해 40웨이브를 버팁니다.

특징

  • 정수 타일 턴제 — 모든 판정은 체스판처럼 타일 단위. 한 웨이브는 플레이어 턴 1번과 적 턴 10번으로 구성됨.
  • 굴러가는 큐브 적 — 적은 큐브이며, 착지했을 때 위에 보이는 면의 효과(자가치유·방어·이동력 등 6종)를 받음.
  • 14문양 × 4컬러 × 5티어 = 280종 타워 — 문양은 무기 6 + 원소 8, 컬러는 공격 방식(광역·단일·버프·디버프).
  • 상점·대기석·자동 합성 — 오토배틀러식 카드 구매, 대기석 12칸, 같은 타워 3기 자동 합성.
  • 시너지 타워 14종 — 문양 3개를 재료로 하는 북유럽 신(오딘·토르·로키 등)의 권능.

적 1턴의 7단계 — TurnManager가 이 순서로 직접 호출

단계이름하는 일
⓪턴 시작타워가 서 있는 칸의 버프존을 다시 모음. 스킬의 "턴 시작" 훅(불 단일의 브레스)
①버프 타워 행동보드 순서로 행동력 소모 → 존 위 타워에 스킬 1 → 스킬 카운트가 차면 스킬 2(아군 전체). TowerTurnRunner.RunBuffTowers
②공격 타워 행동한 기씩: 행동력 → 스킬 2 발동 확인 → 기본 공격 → 투사체(AttackHandle)가 끝날 때까지 기다린 뒤 다음 타워
③적응형 버프살아 있는 적마다 보이는 면 효과를 다시 계산, 착지 뒤 처음이면 자가치유
④적 이동행동 주기가 된 적이 주사위(최소 ~ 최대 이동력)를 굴려 굴러감. 이동 전후 훅(상태 유지 감소, 바람 디버프 등)
⑤디버프 · 타일디버프 타워 행동 → 멈춘 칸의 효과(디버프존 밟기 → 정화·비프로스트)
⑥도트 · 장판화상·출혈 등 지속 피해, 애로우 레인·블랙홀 장판, 지속 시간 감소, 조건부 즉사
⑦턴 종료보스·중간 보스의 제한 턴 감소, 0이면 게임 오버
순서가 곧 규칙이므로 이 단계는 이벤트가 아니라 직접 호출로 구현함. 이벤트로 두면 실행 순서가 "누가 먼저 구독했는가"에 숨어 버림. 무언가 일어난 단계 뒤에만 0.5초 쉬고(TurnManager.m_phaseGap), 시뮬레이션에서는 쉬지 않음.

패턴쓰는 곳쓰는 이유
싱글톤매니저 9개에만씬에 하나뿐인 매니저를 여러 스크립트가 찾음. 씬 단위이며 DontDestroyOnLoad 하지 않음. 계산·상태 클래스는 인자로 값을 받아야 테스트할 수 있으므로 싱글톤으로 만들지 않음
오브젝트 풀적(EnemyPool), 이펙트용 사각형(EffectQuadPool)웨이브 시작에 최대 40마리 동시 소환(한 판 일반 적 720마리), 단일 타워 한 번 행동에 수십 발 → GC 멈춤 방지. 꺼낼 때 지울 목록을 정해 "지난번 상태가 남는" 버그를 막음. 타워는 상태가 많고 한 판 160기 안팎이라 풀을 쓰지 않음

6전투 계산

피해 계산 순서

원래 피해 = Power × 거리 비례 보너스 × 치명타 배율
고정 피해 = 원래 피해 × 고정 피해 전환율
방어 적용 피해 = (원래 피해 − 고정 피해) × 방어 계수 × 받는 피해 배율
최종 피해 = 방어 적용 피해 + 고정 피해

방어 계수 = 1 ÷ (1 + 0.01 × 방어력) (방어력 ≥ 0)
= 1 + 0.01 × |방어력| (방어력 < 0, −100이면 2배)
거리 비례 보너스 = 1 + 보너스% × 타일 거리
  • 방어 관통(%)은 방어력에 먼저 적용: 양수면 줄이고, 음수면 더 음수로.
  • 상한은 두지 않음. 남는 한도는 % 값뿐 — 저항력 100%, 치명타 확률 100%, 방어 관통 100%, 치유 감소 80%.

버프와 디버프의 합산 — 모든 스탯 공통

최종값 = 기본값 × (1 + 버프 %의 합 − 디버프 %의 합)
예) 공격력 10, 버프 +50% · +25%, 디버프 −30% → 10 × (1 + 0.75 − 0.30) = 14.5

곱하지 않고 전부 더하고 뺌. 이 규칙이 StatModifier 목록을 한 번에 더하는 구조의 근거.

공격 방식

컬러동작

12연출과 성능

연출은 전부 DOTween

  • 움직임·회전·크기·튀김·눌림은 while + Lerp 코루틴으로 쓰지 않고 DOTween으로 씀 — 적 큐브 구르기, 소환 낙하, 투사체 비행, UI 연출 모두.
  • 규칙 코드는 트윈을 기다리기만 함(yield return tween.WaitForCompletion()). 피해·점유 같은 규칙은 트윈 콜백이 아니라 규칙 코드가 정함 → 시뮬레이션에서 연출을 꺼도 결과가 같음.
  • 풀에서 꺼내 쓰는 것은 SetLink(gameObject, LinkBehaviour.KillOnDisable)로 꺼질 때 트윈도 끔. 꺼낼 때 트윈이 바꿔 둔 크기·위치·회전을 되돌림.
  • 90°씩 쌓이는 회전은 끝난 뒤 가장 가까운 각도로 맞춤(EnemyCubeMeshVisual.SnapRotation).

표시 원칙

  • 같은 타일의 적은 중앙에 겹쳐 서고, 타일 오른쪽 아래에 "x N"으로 수를 표시. 머리 위 HP 바는 두지 않고 적 정보 패널에서 보여 줌.
  • 월드마다 타워 칸(밝은 바탕)·길(짙은 바탕)·테두리·화살표 색을 스테이지 에셋에 두고, 씬 시작 시 그 색으로 타일맵을 칠함. 메뉴의 판 미리보기도 같은 색을 씀.

15설계 결정 기록 (Q&A)

개발하면서 고민했던 질문과, 그 답으로 실제 어떻게 구현했는지를 정리했습니다.

데이터와 구조

enum의 0번에 None을 꼭 둬야 할까?

C# enum의 기본값은 무조건 0이라, 값을 안 넣은 필드나 인스펙터에 새로 붙인 컴포넌트는 0번으로 시작함. 0번이 실제 값(예: 스토리 모드)이면 "안 골랐다"와 구분할 수 없어 버그가 숨음.

구현모든 enum의 0번은 None. WaveTable의 switch도 None과 default에 0을 돌려줌 → 모드를 새로 더하고 case를 빠뜨리면 적이 체력 0으로 나와 바로 드러남. "빠뜨리면 눈에 띄게"가 원칙.

적 데이터는 ScriptableObject보다 CSV로 읽는 게 낫지 않을까?

무엇을 더 자주 고치느냐로 갈림. 타워는 280종이라 에셋으로 두기엔 너무 많고 그림이 ID로 정해짐 → CSV. 적은 약 30종이고, 웨이브마다 세지는 건 웨이브 배율이 맡아 적마다 숫자는 기본값 몇 개뿐. 대신 그림(큐브 면, 보스 외형)과 보스 기믹이 적마다 다름.

구현타워는 CSV 1티어 56행(TowerDatabase, 열은 헤더 이름으로 찾음), 적은 ScriptableObject(EnemyDefinition). 다른 코드는 정의의 프로퍼티만 읽어서, 나중에 형식을 바꿔도 한 파일만 고치면 됨.

웨이브 배율은 식으로 쓸까, 배열로 쓸까?

식(1 + (순서 − 1) × 0.1)이 짧지만, 표가 일정하게 오를 때만 맞음. 밸런스 조정은 "이 칸만 다르게"가 흔하고, 배열이면 기획서 표와 코드를 나란히 놓고 맞춰 보기 쉬움.

구현WaveTable에 순서 배율 10칸(1.0 ~ 1.9)·사이클 배율 4칸(1 / 2 / 4 / 8)을 배열로 둠. 식에서 배열로 바꿀 때는 테스트를 그대로 두고 결과가 같은지 확인하는 방식으로 속만 바꿈. 이때 정한 원칙: 테스트 정답은 머리로 정하지 않고 기획서의 숫자에서 가져옴(보스 배율을 같은 오해로 코드와 테스트에 함께 적어 초록색인 채 틀렸던 일이 있었음).

칸 크기를 1.5에서 1로 바꿔도 괜찮을까?

규칙은 칸 번호(정수)만 다루므로 그대로. 문제는 옛 코드에 WorldUnitsPerTile = 1.5f가 따로 박혀 있어 사거리가 1.5배로 틀어지는 것 — 같은 값을 두 곳에 적은 결과.

구현칸 → 화면 위치는 늘 타일맵에 물어봄(GetCellCenterWorld). 판정은 Vector3Int(칸), 화면에 그릴 때만 Vector3. 고정 수치는 이름 붙은 상수로(LastWaveEnemyTurns, WaveManager.LastWave).

판과 칸

길 칸의 번호와 좌표를 어떻게 서로 찾을까? 고리는 어떻게 감을까?

번호 → 좌표는 List(번호가 곧 순서), 좌표 → 번호는 Dictionary(클릭한 칸이 몇 번인지). 고리를 감는 식 (i + n) % n은 −41처럼 두 바퀴 넘게 뒤로 간 번호에서 틀림.

구현BoardGrid가 두 장부를 함께 들고, WrapPathIndex = ((i % n) + n) % n. 테스트에 −41 → 39를 넣어 이 경우를 고정. 좌표 → 번호는 없을 수 있어 TryGetPathIndex(false면 out 값은 쓰지 않음).

타워 칸과 길 칸을 같은 방법으로 모을 수 있을까?

타워 칸은 "읽는 순서"(왼쪽 위부터)라 타일맵을 훑기만 하면 됨. 길 칸은 "적이 걸어가는 순서"라 시작점과 방향을 타일만 보고 알 수 없음.

구현타워 칸은 cellBounds(사각형)를 훑으며 HasTile로 진짜 칸만 걸러 자동 수집 → 판이 네모가 아니어도 됨. 길 칸은 인스펙터에 순서대로 적고, 씬 뷰 Shift + 클릭으로 경로 끝에 칸을 더하는 에디터 도구와 Gizmos 번호 표시로 확인.

칸마다 적 목록을 처음부터 배열로 만들어 두는 게 가볍지 않을까?

길 32칸, 적 수십 마리라 속도·메모리는 거의 같음. 배열은 크기 고정이 코드에 드러나는 장점, Dictionary는 칸 번호가 곧 열쇠라 길이 바뀌는 기믹이 생겨도 자리 순서를 맞출 필요가 없는 장점.

구현둘을 견준 뒤 Dictionary로(PathOccupancy). 저장소는 private이라 나중에 속을 바꿔도 이 파일만 고침. 밖에서는 Add로만 넣게 해 "넣으면 반드시 알린다"를 지키고, Move는 두 칸을 다 바꾼 뒤 한 번만 알림.

적

예전처럼 Health·Move·DebuffController로 나누면 안 될까?

나누는 건 같지만 옛 방식은 셋이 나란히 남의 일까지 함(체력이 보상·클리어·풀 반환까지, 이동이 타일 효과까지). 책임자가 없어 초기화 순서가 흩어지고 버그가 생김.

구현EnemyController가 책임자로 부품(EnemyMovement, EnemyHealth, EnemyStats, EnemyStatusEffects, EnemyResistance)을 들고 초기화·정리 순서를 한곳에서 정함. 남의 일은 따로: 보상·풀 반환은 DeathResolver, 타일 효과는 EnemyTileEffectApplier. 이동만 MonoBehaviour이고 나머지는 순수 클래스라 씬 없이 테스트됨.

풀에서 꺼낼 때(OnGet) 바로 켜면 안 될까?

꺼내는 순간은 아직 준비 전. 거기서 켜면 OnEnable이 빈 값으로 돌고, 재사용하는 적은 지난번에 죽은 자리에 한순간 보였다가 옮겨짐.

구현꺼냄(꺼진 채) → Setup(정의·배율) → 위치 → 켜기. 켜기는 준비하는 쪽(EnemySpawner)이, 끄기는 돌려받는 풀이 함. 밖에서 풀에 꼭 알리는 건 Get과 Release 둘뿐.

적 종류마다 프리팹을 만들어야 할까? 보스도?

큐브라면 데이터와 그림만 다름.

구현프리팹 하나 + 데이터 그릇(EnemyDefinition) + 그림(EnemyCubeAppearance). 일반·중간 보스·최종 보스가 같은 풀을 씀. 면 재질 6개는 모든 적이 공용으로 쓰고, 적마다 다른 캐릭터 그림은 MaterialPropertyBlock으로 덮어씀 → 새 스테이지의 적은 Appearance 에셋만 만들면 됨.

큐브 구르기 연출 코드가 너무 길고 복잡한데, 줄일 수 없을까?

꼭 필요한 건 셋뿐: 면의 역할 정하기, 구른 뒤 보이는 면 알기, 90°씩 돌리기. 나머지는 직접 짠 while + Lerp 보간과 대비책.

구현연출을 DOTween으로 다시 씀(DOMove, DORotate, DOPunchScale, DOJump, Sequence). "지금 어느 면이 보이나"는 DOTween이 모르므로 우리 코드로 남김. 이후 모든 연출의 규칙이 됨(12장). 정확한 등속 이동과 부드러운 구르기를 키로 바꿔 가며 비교한 뒤 부드러운 쪽을 유지 — 연출이 이동 규칙과 분리돼 있어 연출을 세 번 바꾸는 동안 규칙 코드는 그대로였음.

이동을 연타했더니 큐브가 엉뚱한 칸에서 45° 돌아간 채 눌려 멈췄다. 왜?

이전 이동이 끝나기 전에 다음 이동이 시작돼 겹친 것. DOTween은 "지금 값에 더하기"라 겹치면 회전·크기가 섞이고, 같은 칸에서 출발한 두 이동이 점유를 서로 뺏음.

구현EnemyMovement.IsMoving으로 이동 중에는 새 이동을 받지 않고, 실제 턴은 TurnManager가 모든 이동이 끝나길 기다림. 회전은 끝난 뒤 가장 가까운 90°로 맞춤(SnapRotation).

효과를 지울 것만 메모해 두었다가 RemoveAll로 한 번에 지우면 되지 않을까?

"목록을 다 돈 뒤 반영"은 같은 생각. 다만 RemoveAll로 전부 지우는 건 정화 타일 전용이고, 보통은 메모한 것만 하나씩 지워야 다른 효과(기절, 출혈)가 남음. 메모에는 "나중에 넣기"도 들어감.

구현EnemyStatusEffects가 순회 중이면 추가·제거를 보류 목록에 적고 끝난 뒤 반영. 순회 표시는 try / finally로 반드시 해제(에러가 나도 "읽는 중"에 갇히지 않게).

전투

치명타 판정을 Random.Range(0, 100) < 확률 × 100으로 하면 안 될까?

정수 100칸 방식은 소수 퍼센트가 틀어짐 — CSV의 5.5%가 6%가 됨. Random.value < 확률은 정확히 5.5%.

구현CriticalRoll을 둘로 나눔: 주사위를 굴려 넘기는 함수와, 굴린 수를 받아 판정하는 함수. 판정 쪽에 숫자를 직접 넣어 테스트로 경계값(0%, 100%)을 고정.

UnityEngine.Random을 쓰다가 특수 타일 배치에서는 왜 System.Random을 쓸까?

Unity의 Random은 게임 전체가 함께 쓰는 주사위 하나라, 시드를 고정해도 중간에 다른 코드가 한 번이라도 굴리면 결과가 달라짐. System.Random은 따로 만들어 넘겨줄 수 있는 "나만의 주사위".

구현특수 타일 배치(SpecialTileLayout.Generate)는 System.Random을 받아 같은 시드면 같은 배치(SpecialTileLayoutTest에서 확인). 밸런스 시뮬레이션에서도 상점 뽑기 난수를 전투 난수와 분리해 비교 실험의 조건을 맞춤.

회복 함수에서 늘어난 체력에서 이전 체력을 왜 빼나?

돌려주는 값을 "실제로 찬 양"으로 하려고. 최대 100, 지금 90에 30을 회복하면 돌려주는 값은 10.

구현EnemyHealth.Heal은 최대 체력을 넘지 않게 자르고 실제 회복량을 돌려줌 → 회복 숫자 표시나 회복량을 읽는 규칙에 그대로 씀.

타워와 표시

투사체 프리팹 28개를 하나로 합치면 애니메이션은 어떻게 하나?

옛 28개에는 Animator가 없었고, 다른 건 그림과 꼬리·파티클 색, 날아가며 도는지뿐 — 프리팹마다 따로 둘 이유가 없었음.

구현처음에는 프리팹 하나 + 번호별 표로 합쳤고, 지금은 한 단계 더 나아가 프리팹 없이 (컬러 + 문양) 번호 → 코드로 그리는 탄 연출 표(ShotEffectTable)를 씀. ProjectileManager.Fire(lookId, …)가 번호로 연출을 찾고, 그림은 풀링한 사각형(EffectQuadPool) 위에 그림.

다발 공격의 위성(발사 대기 탄)을 어떻게 배치할까?

옛 방식은 12 · 6 · 9 · 3시 고정 순서였음. 공격 횟수만큼 12시부터 시계 방향으로 고르게 놓기로 정함.

구현i번째 위성 각도 θ = 360° × i ÷ N, 위치 = (sin θ, cos θ) × 반지름. 띄운 순서대로 같은 간격을 두고 발사.

합성 결과 타워는 무엇을 이어받아야 할까?

합성은 "같은 자리의 타워가 한 단계 오른 것"이라, 플레이어가 정해 둔 것과 쌓아 온 것은 남아야 함. 반대로 수정자 목록을 통째로 복사하면 출처를 알 수 없는 값까지 따라옴.

구현TowerState.CopyInheritedFrom 한 곳에서: 타겟 우선순위·공격 칸·스킬 카운트·성장 카운터는 그대로, 받고 있던 존 버프·시간 버프·영구 효과는 출처별로 수정자를 골라 옮김. 옮기는 동안은 BeginBatch / EndBatch로 스탯 재계산을 한 번만 함.

글자는 TextMeshProUGUI와 TextMeshPro 중 무엇을 쓸까? 대미지 숫자는 적 프리팹에 넣을까?

화면에 붙은 HUD는 UGUI, 게임 세계(판·적) 위의 글자는 월드 TextMeshPro. 대미지 숫자를 적 안에 넣으면 연속 타격이 덮어써지고, 적이 죽어 풀로 돌아가면 떠오르던 숫자도 함께 사라짐.

구현칸의 "x N"은 월드 TextMeshPro(BoardPresenter). 라벨이 적에 가려지는 문제는 Order 숫자를 키우지 않고 Sorting Layer를 UI로 올려 해결. 대미지 숫자는 별도 프리팹 + 풀 + DOTween으로 만들기로 정했고, 아직 구현 전.

설계 원칙과 검증

지금 구조가 SOLID 원칙을 지키고 있나?

단일 책임은 지킴(명단·칸·소환·보관·조립을 클래스 하나씩). 개방-폐쇄는 계속 늘어나는 곳(문양 56종)에만 전략·팩토리로 적용하고, 종류가 셋뿐인 곳은 switch가 더 읽기 쉬움. 원칙은 "고치기 쉽게"를 위한 도구라 모든 곳에 인터페이스를 두면 파일만 늘어남.

구현인터페이스는 구현이 둘 이상이거나 테스트에서 가짜로 바꿔 끼울 때만(ITarget, IProjectileLauncher). Instance는 매니저끼리, Start에서만 씀.

부품을 Instance로 바로 찾으면 짧은데, 왜 생성자로 받나?

Instance는 한 줄로 짧지만, 필요한 부품이 생성자에 안 보이고, 매니저끼리 서로 부르게 되고, 씬 없이 테스트할 수 없음.

구현"부품은 생성자로" — BossTimer, DeathResolver 등 순수 클래스는 필요한 것을 생성자로 받고, 실제로 찾는 일(Instance)은 그것을 만드는 매니저의 Start 한 곳에서만 함.

싱글톤 오브젝트 두 개로 실험하면 늘 같은 쪽이 지워진다. 하이어라키 순서와 관계가 있나?

관계없음. 같은 스크립트끼리의 Awake 순서는 Unity가 보장하지 않음(실험에서는 먼저 만든 오브젝트가 먼저 깨어났지만 약속된 규칙이 아님).

구현Awake 순서에 기대는 코드를 쓰지 않음 — Awake에서는 자기 준비만, 다른 매니저를 찾는 건 Start에서. 옛 코드의 "첫 소환 0마리" 버그가 이 순서 문제였음.

실무에서도 테스트를 이렇게 쓰나? 돌려 보면서 디버깅하는 게 더 흔할 것 같은데.

게임 업계는 둘 다 쓰고 플레이 확인이 더 흔함. 손맛·연출·밸런스·여러 시스템이 엮인 흐름은 플레이로, 계산과 규칙은 테스트로 — 재현하기 어려운 경우(41칸 뒤로 간 적), 나중에 고치다 조용히 깨지는 경우, 기획서 숫자와 맞는지 증명할 때.

구현계산(순수 클래스)만 EditMode 테스트, 화면과 흐름은 플레이 + InvariantChecker + 시나리오(14장).

모든 배치의 전역 최적해를 구할 수 있을까?

구별되는 타워 5기를 28칸에 놓는 경우만 11,793,600가지, 10기면 약 47.6조. 존 위치·구매·합성 순서까지 넣으면 완전 탐색은 불가능. 전역 최적을 말하려면 범위와 목표를 고정하고, 최적성을 보장하는 가지치기(분기한정)나 정수계획이 필요함.

구현현실적인 범위로 좁힘: StrategySearch가 선택 규칙 묶음(구매·판매·배치 우선순위 등)을 최대 500개 탐색. 맵·구매 난수는 시드로 고정하고 전투 난수만 바꾸며, 후보당 최대 10판, 5판째 1위 평균의 80% 미만이면 조기 중단. 전역 최적을 증명하지는 않는다는 한계를 함께 기록.
